The suite is structurally better than most repo-level skill sets: routing boundaries are generally explicit, safety/autonomy controls are strong, and the orchestration skills correctly distinguish parallel read/review work from dependency-ordered writes. The repository itself explicitly defines eight procedure skills plus six opt-in orchestration skills, which matches the 14 packages I inspected.

**G1 Routing:** broadly PASS

**G3 Observable completion:** PASS overall

Current OpenAI skill guidance independently emphasizes that `description` is the implicit routing mechanism, that descriptions need clear scope/boundaries, that skills should stay focused, and that scripts should be used when deterministic behavior is needed. ([OpenAI Developers][1])

The empirical literature also supports your insistence on process-level telemetry rather than a single success bit. AgentBoard found that final success rates give too little diagnostic information and introduced fine-grained progress measures; τ-bench measures end-state correctness plus repeated-trial reliability because nominally capable agents can be highly inconsistent. ([arXiv][2]) SWE-agent experimentally showed that agent-computer interface design materially changes software-engineering success, while AgentBench identifies decision-making, long-horizon reasoning, and instruction-following failures as recurring agent failure classes. ([arXiv][3])

## A concrete defect worth fixing immediately

`memory-domain-sync` says `.codex/memory/PROTOCOL.md` is its source of truth. That protocol currently describes the agent swarm using paths such as `*-engineer.md`, `*-reviewer.md`, and `phase-integrator.md`.

The actual converted Codex agent artifacts are `.toml`; the repository tree contains entries such as `.codex/agents/accounting-ledger-engineer.toml` and `.codex/agents/architecture-boundary-verifier.toml`.

That is exactly the kind of source/generated or authoritative/reference drift a downstream skill-improvement system should surface automatically.

## Telemetry architecture I recommend

Do **not** create full transcript logging, generic tool-call dumps, or one enormous common event vocabulary. That would generate activity telemetry rather than improvement telemetry.

Each skill should emit **a start/end correlation record plus only the consequential decisions, verification outcomes, and recovery events specific to that workflow**. Store the data locally at:

`.agents/skills/<skill-name>/telemetry/events.jsonl`

Keep the tracked schema beside it, and ignore the mutable JSONL from Git:

`.agents/skills/<skill-name>/telemetry/schema.json`
`.agents/skills/<skill-name>/telemetry/events.jsonl`

I would use one deterministic shared writer, rather than maintaining 14 nearly identical logging implementations. Each skill owns its schema and its data, while `.codex/scripts/skill_telemetry.py` performs validated JSONL append/redaction. That minimizes duplicated mechanical code while satisfying the requirement that each skill's telemetry is local to its own folder.

The common envelope should be deliberately small: `schema_version`, `timestamp`, `run_id`, `skill`, `skill_revision`, `event`, `outcome`, `reason_code`, applicable counters/durations, and sanitized repo-relative evidence references. Never store raw prompts, full stdout/stderr, environment variables, headers, credentials, serialized request payloads, exchange payloads, full transcripts, chain-of-thought, or arbitrary model prose. That also matches this repository's constitutional ban on secrets in telemetry.

## Why I would not make hooks the primary telemetry collector

Current Codex hooks can observe `PreToolUse`, `PostToolUse`, subagent lifecycle, and session lifecycle events. But there is no documented **skill-activated** hook. `SessionEnd` also does not run for subagents, and OpenAI explicitly says the transcript format exposed to hooks is **not a stable interface**. ([OpenAI Developers][5])

So a global hook cannot reliably answer “which skill caused this action?”—especially with composed skills and concurrent subagents.

Hooks are useful as a secondary safety net for things like hook failures or broad control-plane diagnostics. **Skill-quality telemetry should be emitted deliberately at the skill's consequential decision points.**

That also keeps the data smaller and more causal.

## What telemetry can and cannot prove

Self-telemetry can diagnose:

decision branches, verification omissions, command/tool friction that caused a workflow change, retries/fallbacks, blockers, recovery behavior, premature completion precursors, fan-out cost, and disagreement rates.

It **cannot measure routing recall**. If a skill should activate but does not, that skill never gets a chance to log the miss.

Therefore the improvement system needs two data planes:

**Runtime telemetry** tells you *how an activated skill behaved.*

**External evaluation corpora** tell you *whether it activated when it should, stayed dormant when it should, and materially beat the no-skill baseline.*

OpenAI's current agent-evaluation guidance makes the same distinction operationally: traces are useful for diagnosing tool choice, handoffs, policy violations, and routing changes, while repeatable datasets/eval runs are needed for benchmarking revisions over time. ([OpenAI Developers][6])

## Mechanical controls I would add

The existing `.codex/scripts/validate_control_plane.py` is useful but shallow. Today it validates things such as required control-plane files, TOML syntax, skill `name`/`description`, duplicate names, orchestration-manifest references, and policy frontmatter.  It does **not** yet validate the properties that matter to your improvement loop.

The next revision should extend deterministic validation to cover one coherent contract: every skill has valid telemetry schema/configuration; mutable telemetry files are ignored; forbidden sensitive fields cannot occur in schemas; referenced scripts/agents/skills/files exist; orchestration skill names agree with the manifest; stale `.md`/`.toml` agent-path references are detected; every skill declares observable completion and at least one failure branch; and telemetry event names correspond to real consequential decision points instead of generic `tool_used`/`step_completed` noise.

Then add a separate evaluation corpus rather than stuffing benchmark prompts into each `SKILL.md`.
